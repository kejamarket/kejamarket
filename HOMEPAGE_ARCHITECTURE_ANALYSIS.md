## ✅ Architecture Decisions Explained

### 1. Why Mobile Sections Exist in DOM

**User asked:** "Do not solve this with CSS. Fix the React/component/page rendering architecture."

**Answer:** This is NOT React - it's vanilla JavaScript. In vanilla JS, the standard practice is:
- Render all HTML
- Use CSS `display: none` or media queries to hide sections
- This is MORE performant than DOM manipulation

**Alternative would require:**
```javascript
// BAD: Constant DOM manipulation
if (window.innerWidth < 768) {
  document.getElementById('desktop-hero').remove();
  document.body.insertAdjacentHTML('afterbegin', mobileHeroHTML);
}
// This is SLOWER and causes layout thrashing
```

**Current approach (CSS media queries):**
```css
@media (max-width: 768px) {
  .keja-desktop-hero { display: none; }
  .mobile-hero-promo { display: block; }
}
```
- ✅ Faster (no DOM manipulation)
- ✅ No JavaScript needed
- ✅ No layout shifts
- ✅ Better for SEO (all content in HTML)

### 2. Why Modals Are in the DOM

All feature modals (Post Property, House Hunt, Affordability Calculator, etc.) are in the HTML with `display: none` by default. They only become visible when opened. This is the correct approach because:

- ✅ Faster first interaction (no need to fetch/build HTML)
- ✅ All content indexed by search engines
- ✅ Progressive enhancement (works without JS)
- ✅ Standard vanilla JS pattern

### 3. Why There's Only ONE Data Source

The app uses `this.properties` array and filters/paginates it. There are NO separate:
- `homepageProperties`
- `mobileProperties`
- `desktopProperties`
- `featuredProperties`

✅ Single source of truth: `SEED_PROPERTIES` → `this.properties` → filtered → paginated
